> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn `ger1e/personal-site-lp` into the canonical, well-documented personal site repository; reposition `ger1e/landing-pages` as the experimental/history repo; add lightweight structural QA without dependency bloat; and prepare the profile README path for `ger1e/ger1e`.

**Architecture:** Keep both sites static and framework-free. `personal-site-lp` gains documentation, repository hygiene, and a standard-library Python QA harness invoked by GitHub Actions. `landing-pages` receives documentation-only repositioning. All implementation work happens on `pimp-my-git-2` branches and is merged only after verification.

**Tech Stack:** Static HTML/CSS/JavaScript, Python 3 standard library, GitHub Actions YAML, Markdown.

**Spec:** `docs/superpowers/specs/2026-08-21-pimp-my-git-2-design.md`

<a id="global-constraints"></a>
<sub><strong>01 // Global Constraints</strong></sub>

- `ger1e/personal-site-lp` remains the canonical public personal-site repository.
- Do not add a frontend framework, package manager, build system, or runtime dependency.
- Do not add byte-for-byte SHA256 assertions to routine QA.
- Preserve restrictive CSP, keyboard-visible focus behavior, responsive behavior, and `prefers-reduced-motion` support.
- Do not add analytics, telemetry, secrets, fake metrics, contribution generators, star farming, or badge walls.
- `ger1e/cti-enrichment-gateway` remains private and is not broadly redesigned in this pass.
- Avoid destructive cleanup unrelated to presentation or correctness.

<a id="task-1-canonical-site-qa-harness"></a>
<sub><strong>02 // Task 1: Canonical-site QA harness</strong></sub>

**Files:**
- Create: `.github/workflows/qa.yml`
- Create: `tests/test_qa.py`
- Create: `scripts/qa.py`

**Interfaces:**
- Consumes: repository root and `index.html`.
- Produces: `scripts.qa.audit_repository(root: pathlib.Path) -> list[str]`; an empty list means the repository passes structural QA.

- [ ] **Step 1: Add the workflow configuration**

Create `.github/workflows/qa.yml` to run on pushes and pull requests to `main` and `pimp-my-git-2`. Use Ubuntu and Python 3.12, then run `python -m unittest discover -s tests -p 'test_*.py' -v` followed by `python scripts/qa.py`.

- [ ] **Step 2: Write the failing tests**

Create `tests/test_qa.py` that imports `audit_repository`, copies a minimal valid fixture into a temporary directory, and verifies that the audit reports no failures for valid content and reports failures for missing document structure, merge-conflict markers, `.env` files, and missing local assets.

- [ ] **Step 3: Verify RED**

Push the tests before `scripts/qa.py` exists and verify that GitHub Actions fails because `scripts.qa` cannot be imported. This proves the tests exercise the not-yet-implemented QA interface.

- [ ] **Step 4: Implement the minimal QA module**

Create `scripts/qa.py` using only Python standard-library modules. It must check:

```text
README.md exists
index.html exists and is non-empty
<!doctype html>, <html, <head, and <body are present
no <<<<<<< / ======= / >>>>>>> merge-conflict markers
no .env file is committed
relative src/href asset references resolve when they point at repository-local files
index.html contains prefers-reduced-motion
index.html contains :focus-visible
index.html contains a Content-Security-Policy meta tag
```

The CLI exits `0` with `QA PASS` when `audit_repository()` returns an empty list; otherwise it prints each failure and exits `1`.

- [ ] **Step 5: Verify GREEN**

Confirm the workflow passes on the implementation commit and the CLI produces `QA PASS` against the repository.

<a id="task-2-canonical-site-repository-presentation-and-hygiene"></a>
<sub><strong>03 // Task 2: Canonical-site repository presentation and hygiene</strong></sub>

**Files:**
- Modify: `README.md`
- Create: `.editorconfig`
- Create: `.gitattributes`
- Create: `.gitignore`
- Create: `SECURITY.md`

**Interfaces:**
- Consumes: the existing static site implementation.
- Produces: a self-explanatory public repository with consistent text-file behavior and a clear vulnerability-reporting policy.

- [ ] **Step 1: Replace the placeholder README**

Document: project identity, purpose, implementation model, local usage via `python -m http.server 8080`, deployment assumptions, accessibility, security/privacy posture, repository structure, and canonical links. Keep the tone technical and concise; do not add generic badges.

- [ ] **Step 2: Add editor and Git normalization**

Use UTF-8, LF, final newlines, and two-space indentation for HTML/CSS/JS/YAML where editor configuration applies. Keep binary files marked binary through `.gitattributes` patterns.

- [ ] **Step 3: Add ignore rules**

Ignore OS/editor junk, Python caches, local `.env*` files except `.env.example`, temporary files, and local static-server logs. Do not ignore tracked site assets.

- [ ] **Step 4: Add `SECURITY.md`**

State that the repository is a static personal site, request responsible private disclosure through GitHub's supported private reporting path when available, explicitly prohibit publishing secrets or exploit details in public issues, and clarify that third-party services linked/embedded by the site are outside this repository's security boundary.

- [ ] **Step 5: Run QA**

The workflow and `python scripts/qa.py` must remain green after documentation/hygiene changes.
